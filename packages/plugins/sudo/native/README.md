# Native authentication boundary

OpenCode must not collect, forward, buffer, or serialize the sudo password. The JavaScript plugin handles command metadata and command results only. This is a structural boundary, not a claim that a compromised operating system or terminal cannot steal a password.

The server creates a private, per-request Unix socket. The native supervisor takes the terminal, then connects locally and claims the request before permitting authentication. Failed claims restore the acquired terminal state and return automatically. A hostname match or shared filesystem is not sufficient: an actual local Unix socket connection is required. A TUI running on a different machine must be run on the server through SSH instead.

After the TUI suspends input, the supervisor takes the terminal foreground process group and claims the same immutable request that the user approved in OpenCode. Linux disables echo during the handoff. macOS preserves the inherited terminal settings and lets sudo/PAM control password echo: disabling echo before invoking sudo prevented the Touch ID dialog from focusing in both Ghostty and Apple Terminal. Only `/usr/bin/sudo` reads the authentication input, directly from `/dev/tty`. Its stdout and stderr also go directly to the terminal; PAM conversation output is never a tool result.

After authentication, a second mode of the installed helper redirects command output into a private FIFO, starts the command in a new session without a controlling terminal, and supplies `/dev/null` as stdin. The supervisor forwards only that FIFO's bytes to the server. After completion, cancellation, or authentication failure, the supervisor reaps sudo, disables echo for macOS cleanup, restores presentation, flushes unread input while restoring terminal attributes with `TCSAFLUSH`, verifies the attributes by reading them back, then restores and verifies foreground ownership. On macOS, echo between password prompts and during command execution follows system sudo's behavior. OpenCode resumes automatically only after helper exit zero certifies this cleanup. The command exit status remains a separate result. Failed restoration or unexpected child-wait failure leaves OpenCode suspended.

The release package includes a static Linux x64 executable and a macOS arm64 executable linked against the system library. No root installation, setuid bit, install hook, or end-user compiler is required. The package is trusted code, as are OpenCode's JavaScript plugin files. A checksum catches damaged/mixed assets; it is not an independent trust anchor against someone who can replace the whole package.

On Linux, the native supervisor builds `/proc/<its-own-pid>/exe` before forking sudo and keeps running through sudo completion. Sudo executes that running image after authentication; replacing or deleting the package pathname cannot substitute another executable for that handoff. Linux documents this executable reference in [proc_pid_exe(5)](https://man7.org/linux/man-pages/man5/proc_pid_exe.5.html). Proc access failures fail closed. The post-authentication entry still requires root and refuses setuid/setgid invocation. A test-only build substitutes unprivileged fake sudo and is never released.

On macOS, the TUI reads and verifies helper bytes before terminal suspension, stages them in an independent private mode-0700 directory with executable mode 0500, and launches that image. `_NSGetExecutablePath` supplies its pathname to sudo. The staged copy remains until native completion, including cancellation and failure, then is removed. Package replacement, deletion, and in-place writes cannot change the staged bytes. This preserves the existing same-user trust boundary; the temporary copy is not a defense against compromised same-user code. macOS release builds use the linker's ad hoc signature, verify it with `codesign`, then compute the checksum. No Developer ID notarization is claimed for other distribution paths.

Touch ID stays inside Apple's system sudo/PAM flow. The plugin has no biometric API or password transport and makes no PAM configuration changes. A session where stock sudo cannot use Touch ID can use the configured password fallback.

Trusted components remain the operating system, terminal/SSH/tmux, sudo/PAM, installed plugin and bundled native helper, OpenCode code, and the user-approved root command. Killing or compromising these components is outside the confidentiality guarantee. Passwords typed into the chat composer or before the native sudo prompt are outside the flow.

The native panel receives only a fresh completed, bounded sanitized pre-authentication snapshot and numeric theme colors on a one-way descriptor, which is closed before forking sudo. It never reads the terminal screen. Resize uses ioctl, resets scrolling margins, and leaves all password input to sudo. The snapshot can be absent without weakening terminal custody.

Ctrl+C cancels while sudo is active. Once the child is reaped, cancellation signals are blocked during cleanup so late cancellation cannot interrupt restoration or signal a reused PID. JavaScript stays suspended throughout authentication and execution, discards its unread stream buffer before resume, and never reads authentication output. No final keypress or delay is required. Input arriving after resumption belongs to the restored session; the implementation does not identify arbitrarily delayed password bytes.

Some package managers apply the installing user's umask and unpack the helper as mode 0775. The plugin removes group-write permission from a helper owned by that same user before verifying its digest and using it. Other-owner group-writable, world-writable, setid, nonregular, and nonexecutable helpers remain rejected. This is local permission tightening, not an install hook or privileged setup.
